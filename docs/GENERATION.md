# 자료 생성 지침 (매일 08:45)

앱은 **읽기 전용 정적 사이트**입니다. 매일 아침 자동 작업이 아래 파일을 만들어 GitHub `main`에 올리면 Cloudflare가 자동 배포하고, 앱이 그 파일을 읽습니다.

```
08:45 자동 작업
  ① 언어별로 따로: (목표 단어 선정 + 통합 글 작성) → 별도 품질 점검
  ② data/days/YYYY-MM-DD.json 저장   (스키마 v2)
  ③ node tools/finalize.mjs <파일>   ← 단어 강조 위치(start/end) 계산
  ④ node tools/validate.mjs <파일>   ← 코드 검증 (오류가 있으면 수정, 최대 3회)
  ⑤ node tools/build-index.mjs       ← data/index.json 갱신
  ⑥ git add data && git commit && git push origin HEAD:main
```

실패하면 `node tools/build-index.mjs --failed YYYY-MM-DD "원인"` 으로 표시하세요(앱에 "생성 실패"). 파일도 index 항목도 없는 날은 "자료 없음"입니다.

## 통합 글 원칙

- 단어마다 독립 예문을 만들지 않습니다. 그날의 **모든 목표 단어를 사용한, 하나의 상황·주제로 이어지는 짧은 글**(이야기·대화·말하기 답변)을 씁니다.
- 길이는 **5~6문장**이 기본, 자연스러움과 수준에 따라 4~8문장까지 허용합니다.
- **단어를 먼저 고른 뒤 글에 끼워 넣지 말고**, 처음부터 한 장면에서 함께 쓰기 좋은 단어들을 고릅니다. 억지로 끼운 문장이 있으면 단어 또는 문장을 바꿉니다.
- 목표 단어 외의 어휘·문법도 해당 언어의 수준을 넘지 않게 합니다.
- 모든 목표 단어를 **최소 한 번** 사용합니다. 같은 단어가 여러 번 나오면 나온 곳마다 `uses`에 연결합니다.
- 최근 14일에 나온 단어(`data/days/*.json`)는 피합니다.

### 언어별 지침

**광둥어 — 완전 초급**
- 홍콩 광둥어 **구어**. 발음은 **Jyutping + 성조 숫자 1–6**(음절 공백).
- **표기는 간체**입니다(학습자가 간체로 배우기 때문). 단, **간체로 표현할 수 없는 글자는 번체(원래 글자) 그대로** 씁니다.
  - 표준 간체가 있는 글자 → 간체: `飯→饭 幾→几 錢→钱 該→该 闆→板 話→话 講→讲 飲→饮 廳→厅 點→点 學→学 …`
  - 광둥어 고유 글자(표준 간체가 없음) → 그대로: `嘅 啲 嘢 咗 冇 哋 佢 喺 畀 嚟 咁 嘥 啱 靚 睇 乜 噉 嗰 …`
  - 간체로 바꾸면 다른 글자와 혼동되는 `係`(이다)도 그대로. (예: `你好`, `食饭`, `奶茶`, `几多钱`, `唔该`, `我係学生`)
- 문장은 짧고 단순하게(한 문장 한자 14자 이하 권장). 일상 장면: 식당, 가게, 이동, 인사, 숫자.
- 표준중국어를 한자만 바꾼 문장(書面語) 금지. 예) ✗ 我不是學生 → ✓ 我唔係學生. `係 唔 冇 咗 嘅 佢 我哋 呢 嗰 啲` 등 실제 구어 사용.
- **글의 모든 문장에 Jyutping**(`reading`)을 넣습니다.

**영어 — 토익스피킹**
- 단어는 `/…/` IPA. 글은 토익스피킹 **의견 말하기·상황 설명·사진 묘사 답변**처럼 읽히는 자연스러운 말하기 문장.
- 어려운 문어체·학술 어휘 금지. 문장은 28단어 이하 권장.
- 시제·복수형 등 활용은 허용합니다. 활용형도 `uses`에서 **원래 목표 단어의 ID**로 연결합니다(예: `{"wordId":"en-5","text":"collaborated"}`).

**중국어 — HSK 4~6급**
- 단어·글은 **간체**, 발음은 **성조 부호 병음**(`zǎocān`, 경성은 부호 없음, 숫자 금지).
- 적용 기준은 **HSK 2.0(6급제) 4~6급**. 세트에 `hskStandard` 로 명시하고 앱 화면에도 표시됩니다.
- 광둥어 글자·어휘(`嘅 唔 係 咗 冇 佢 啲 嘢 哋` …) 금지.
- **글의 모든 문장에 병음**(`reading`)을 넣습니다.

**일본어 — 완전 초급 (JLPT N5 이하)**
- 학습자는 **한자를 읽지 못합니다.** 그래서 **한자가 들어간 모든 단어·문장에 후리가나(히라가나)** 를 붙입니다. 한자는 정말 필요한 것만 쓰고, 가능하면 히라가나로 씁니다.
- 어휘·문법: 인사, 음식, 숫자, 이동, 가게·카페 등 기초 생활. `〜です/〜ます/〜をください` 정도의 아주 쉬운 구조. 문장은 짧게(24자 이하 권장), 한 문장 한자 4자 이하.
- 한자는 JLPT N5 범위(검증기에 N5 한자 목록이 있고, 밖의 한자는 경고). 가타카나 외래어(`コーヒー`)도 단어로 좋습니다.
- `word`에는 평소 표기(`食べる`, `水`, `コーヒー`), `reading`에는 **가나로만 쓴 읽기**(`たべる`, `みず`; 가타카나 단어는 그대로).
- **한자가 있으면 `ruby` 배열**로 후리가나를 적습니다(아래 형식). 한자가 없는 단어·문장은 `ruby`를 쓰지 않고 `reading`이 `word`/`text`와 같습니다.
- 글의 모든 문장에 `reading`(가나로만 쓴 전체 읽기, 문장부호 포함)을 넣습니다.
- 목표 단어의 **활용**(`食べる`→`食べます`)은 허용하며, `uses`에서 원래 단어 ID로 연결합니다(예: `{"wordId":"ja-4","text":"食べ"}`).

## 파일 형식 — `data/days/YYYY-MM-DD.json` (schemaVersion 2)

[examples/day.example.json](../examples/day.example.json) 참고.

```jsonc
{
  "schemaVersion": 2,
  "date": "2026-10-02", "status": "ready", "generatedAt": "2026-10-02T08:46:00+09:00",
  "sets": {
    "yue": {                       // en, zh 도 같은 구조
      "lang": "yue",
      "level": "완전 초급",          // data/config.json 의 levels.<언어>.label 과 정확히 같아야 함
      "hskStandard": "…",          // zh 만 필수
      "words": [ { "id": "yue-1", "word": "你好", "reading": "nei5 hou2", "meaning": "안녕하세요", "pos": "인사" } ],
      "passage": {
        "title": "喺茶餐廳", "titleKo": "차찬텡에서", "situation": "식당에서 주문하기",
        "sentences": [
          { "text": "你好！我想食飯。", "reading": "nei5 hou2! ngo5 soeng2 sik6 faan6.", "ko": "안녕하세요! 저 밥 먹고 싶어요.",
            "uses": [ { "wordId": "yue-1", "text": "你好" }, { "wordId": "yue-2", "text": "食飯" } ] }
        ]
      }
    }
  }
}
```

- 단어 `id`: `yue-1`…`yue-5`, `en-1`…`en-10`, `zh-1`…`zh-10`, `ja-1`…`ja-5`. 같은 날짜·언어의 `words`와 `passage`가 **하나의 학습 세트**입니다.
- `uses`: 그 문장에서 쓰인 목표 단어. `text`는 **원문에 실제로 있는 표현**이고 **글에 나오는 순서대로** 적습니다. 목표 단어가 없는 문장은 `[]`.
- `start`/`end`(원문 글자 위치)는 **직접 쓰지 않습니다.** `node tools/finalize.mjs` 가 채웁니다. 앱은 이 위치가 원문과 일치할 때만 단어를 강조합니다(단순 문자열 치환을 쓰지 않음).
- **일본어 `ruby`(후리가나)**: 단어와 문장에서 한자가 든 조각에만 `r`(가나)을 붙인 배열입니다. `t`를 이으면 `word`/`text`, `r ?? t`를 이으면 `reading`이 되어야 합니다(검증기가 확인).
  ```jsonc
  { "id": "ja-3", "word": "水", "reading": "みず", "meaning": "물", "ruby": [ { "t": "水", "r": "みず" } ] }
  { "text": "今日、カフェに行きます。", "reading": "きょう、カフェにいきます。", "ko": "오늘 카페에 가요.",
    "ruby": [ { "t": "今日", "r": "きょう" }, { "t": "、カフェに" }, { "t": "行", "r": "い" }, { "t": "きます。" } ], "uses": [] }
  ```
  단어 강조(`uses`)는 후리가나가 붙은 한자 덩어리(`今日`, `行` …)를 **통째로** 연결해야 하고 한가운데를 자를 수 없습니다.
- 한 번 올린 날짜의 `id`는 바꾸지 마세요. 완료 기록이 `날짜|id`(단어)와 `날짜|언어`(글 읽기)로 저장됩니다.

## 코드로 검증하는 것 (`tools/validate.mjs`)

- 광둥어 5 · 영어 10 · 중국어 10 · 일본어 5 개수, 세트·글·필수 필드(ID, 단어, 발음, 한국어 뜻, 문장 원문·번역)
- 광둥어·중국어·일본어 **문장별 발음 누락**, Jyutping/병음 형식(성조 숫자·부호), 일본어 읽기는 가나만
- **일본어 후리가나**: 한자에 `ruby` 누락, `t` 이은 글 = 원문, `r ?? t` 이은 글 = `reading`, 한자 없는 조각에 `r` 금지, 한자 없는 단어·문장은 `reading` = 원문, 후리가나 덩어리 중간을 자르는 강조 금지
- 일본어 수준 휴리스틱(경고): 문장 24자 초과, 문장당 한자 4자 초과, JLPT N5 목록 밖의 한자
- `uses` 가 **원문과 일치**하는지(`start/end` 위치의 글자 = `text`), 존재하지 않는 단어 ID, 겹침·순서
- **모든 목표 단어가 글에 실제로 사용**됐는지(연결 정보 + 원문 이중 확인)
- 연결되지 않은 목표 단어 출현(강조 누락) 경고
- 광둥어·중국어 모두 간체(번체에만 있는 글자는 오류; 광둥어 고유 글자는 허용), 중국어에 광둥어 글자 혼입, 광둥어 글에 표준중국어식 표현 의심
- 세트 `level` 이 설정(`data/config.json`)과 같은지, 중국어 `hskStandard` 명시 여부
- 연결된 글 여부(휴리스틱): 문장마다 단어가 정확히 1개씩이면 "독립 예문 나열" 경고
- 문장 길이 상한(수준 부적합 의심) 경고, 4~8문장

## 코드로 검증할 수 없는 것 → 별도 품질 점검 (생성과 다른 단계에서 수행)

1. **글이 하나의 상황으로 자연스럽게 이어지는가?** 억지로 끼운 문장·단어는 교체
2. **수준이 맞는가?** 광둥어는 완전 초급이 이해할 수 있는가, 영어는 토익스피킹 답변으로 쓸 만한가, 중국어는 HSK 4~6급(2.0) 범위의 단어·문법인가. *(HSK 단어표와의 자동 대조는 하지 않습니다 — 이 단계의 판단에 의존합니다.)*
3. **광둥어**: 홍콩 사람이 실제로 말할 구어인가, Jyutping 성조가 맞는가, 간체로 바꿀 수 있는 글자를 번체로 남기지 않았는가(코드는 대표 글자만 검사)
4. **중국어**: 병음 성조가 맞는가, 광둥어 표현이 섞이지 않았는가
4-2. **일본어**: 후리가나(읽기)가 실제 읽기와 맞는가(예: 今日=きょう), 문법·어휘가 완전 초급(N5 이하)인가, 한자를 불필요하게 쓰지 않았는가, 자연스러운 일본어인가
5. **영어**: IPA가 맞는가
6. 한국어 뜻·번역이 정확하고 자연스러운가
